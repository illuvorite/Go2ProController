> 适用范围：本仓库 `client/`（C++ WebRTC 控制管理台）+ 网页端编导台
> 相关文档：多机连接与排查见 [`multi_go2_pro_solution.md`](multi_go2_pro_solution.md)；
> 协议细节见 [`go2_webrtc_protocol.md`](go2_webrtc_protocol.md)

## 0. 这是什么

**多机编队表演系统**：把多台机器狗按一条**统一时间轴**编排起来，做动作、换队形、走位，
并让灯光 cue 与动作对齐。对标智身科技（GENISOM AI）2026-08 发布的
「**SomaFlow 多机舞蹈表演系统**」。

它与仓库里已有的「舞蹈编排」是**两套并存**的东西，不是替代关系：

| | 舞蹈编排（`core/dance.hpp`） | 多机编队演出（`core/show.hpp`） |
|---|---|---|
| 语义 | 单机，一串 `{动作, 延时}` 按顺序播 | 多机，绝对时间轴 + 队形 + 角色 + 灯光 |
| 时间 | 累加 sleep（第 N 步会越拖越偏） | 绝对时刻 `t0 + beat × 一拍`（误差不累积） |
| 多机 | 逐台串行下发（第 N 台晚 N×发送耗时） | 同一条 cue **并行**下发 |
| 队形 | 无 | 舞台位 + 编队 + 换位（开环位移） |
| 灯光 | 无 | 灯光 cue（联动链路） |
| 存储 | `robot_dances.json` | `robot_shows.json` |
| 来源 | 复刻参考实现「天树探界遥控」的编排页 | 本次新增 |

## 1. 能力对照：SomaFlow 的五件事，我们做到哪一步

> ★ 这一节要写清楚**哪些是真的、哪些只是链路** —— 现场放鸽子比功能少更糟。

| SomaFlow 的能力 | 本仓库的实现 | 真实程度 |
|---|---|---|
| **动作同步** | 绝对时间轴调度 + 同拍并行下发 + 错位度量 | ✅ 完整实现，同步误差**可测**（见 §3） |
| **空间移动** | 开环位移（前进/左移/原地转），舞台位换位 | ⚠️ **开环**，无里程计闭环（见 §4） |
| **动态编队** | 舞台位图 + 编队指派 + 换位位移 + 静态校验 | ✅ 数据与编排完整；执行仍是开环 |
| **可视化编导** | 网页端编导台：舞台俯视图 + 拍格时间轴 | ✅ 完整实现 |
| **灯光联动** | `LightSink` 抽象 + 时间轴触发 | ⚠️ **只有联动链路，没有驱动**（见 §5） |

**SomaFlow 本体是闭源的**（2026-08-25 只发了一条官方微博，官网至今没有产品页、
规格、定价或 SDK）。所以这里不是"移植"，是**按公开描述的能力集做功能对标实现**。

## 2. 数据模型（`client/core/show.hpp`）

```
Show（一场演出）
 ├── bpm / beats            节拍与总拍数
 ├── cues[]                 时间轴
 │    ├── kind = Action     做一个动作（动作 key）
 │    ├── kind = Move       走一段（开环位移）
 │    ├── kind = Light      触发一个灯号
 │    ├── beat              落在第几拍
 │    └── roles[]           参与角色（设备键列表；空 = 全体）
 └── formations[]           编队
      ├── slots[]           舞台位：id / 名称 / x / y / 朝向
      └── assign{}          哪台狗（设备键）站哪个位
```

### 坐标系（整套编队算术的地基，方向搞反整场队形就是镜像的）

- 舞台坐标：**x 向右（东），y 向前（北）**，单位米，原点在舞台中心。
- 朝向 yaw：**逆时针为正**，0 表示面朝 +y（北）。
- 机器人自身坐标系（协议口径）：**x = 前进、y = 左移、z = 左转**。

换算（`slotTransfer()`）：朝向向量 = `(−sin θ, cos θ)`，左方向 = `(−cos θ, −sin θ)`。
即 θ=0 面朝北、左方为西；θ=+90 面朝西（= 左转 90°）、左方为南。

### 为什么用「设备键」而不是 IP

编队指派与角色都用 `sn:<SN>` / `ip:<IP>`（`UiState::deviceKeyFor`）：

> IP 会随 WiFi / DHCP 变。编队是**演出资产**，不能因为换网络就散架。
> 手写 cue 时直接粘裸 IP 也认（`roleMatches` 两种都收），少一个"填了却不生效"的坑。

## 3. 同步是怎么做的（这一节是整套东西的核心）

### 3.1 三个关键改动

现有「舞蹈编排」的节奏是「发一条 → sleep(延时) → 发下一条」，有两个硬伤：

1. **误差累积**：sleep 的实际时长 ≥ 请求时长，N 步之后整体比音乐慢一大截，越演越偏。
2. **多机不同步**：`forEachSelected` 是**串行**的 —— 第 N 台比第 1 台晚
   N×(单次发送耗时)。3 台、每步 30ms，就是 90ms 错位。

本实现改成：

| | 做法 | 效果 |
|---|---|---|
| **绝对时间轴** | 每条 cue 的触发时刻 = `t0 + beat × 一拍时长`；调度线程只负责「等到点了就发」 | 误差**不累积**（`testAbsoluteTimelineNoDrift` 钉死） |
| **并行群发** | 同一条 cue 的多台狗**同时**下发（每台一个线程） | 错位只剩网络抖动本身，不再叠加发送耗时 |
| **可度量** | 记录每条 cue 各狗"写出去的时刻"，算最大/平均错位、迟到条数 | **同步必须可测，否则只是宣传语** |

### 3.2 同步度量（`ShowSyncMetrics`）

网页端顶栏实时显示：

- `最大错位 ms` —— 同一条 cue 内，各狗指令发出时刻的最大差
- `平均错位 ms` —— 各 cue 错位的平均（按**真正量到错位的 cue 数**算，不按 cue 总数，
  否则没有目标的那一拍会把平均值稀释得好看但失真）
- `迟到条数` —— 触发时已经过点的 cue 数（调度被拖慢了，机器卡 / 线程被抢占）

同网段实测的网络抖动是 10~40ms 量级；一台机器狗 120BPM 时一拍 500ms，
错位远小于一拍 —— 这是"能上台"的前提。

### 3.3 为什么是「拍」而不是「秒」

演出的时间跟着音乐走，而音乐有 BPM。编导按拍编排（"第 8 拍全体敬礼"），
换一首歌只要改 BPM 与拍数，编舞不用动。后端把拍换算成绝对时刻。

## 4. 空间移动：为什么是**开环**的（一条硬约束，先讲清楚）

Go2 的 sport 接口**没有绝对定位**。本仓库解析的状态话题
（`core/telemetry.hpp`：`rt/lf/lowstate` / `rt/sportmodestate`）里只有
**电量、温度、姿态角、偏航角速度、运动模式、进度** —— **没有 x/y 里程计**。

所以这里**不做闭环导航**，做的是**开环位移**（dead reckoning）：

- 编导在舞台图上定好位（哪台狗站哪个 x/y/朝向），系统算出
  「前进几米 / 左移几米 / 原地转几度」，按开环速度指令走完；
- 执行分**两段**（顺序执行，不并行）：
  ① 平移段（按 `speedMs` 走）→ ② 转向段（按 `turnRateDegS` 转）。
  ★ 四足**不能一边横移一边原地转** —— 那等于让它横着走同时自旋，四条腿落点会打架；
  舞台上的真实做法也是"先挪到位，再转身面向观众"。
- 舞台坐标图（`StageSlot` 的 x/y/yaw）用来**画**队形、**校验**位移量，
  而不是实时闭环纠偏。

### 静态校验为什么必须存在

开环执行**不会报错**，只会**走不到位**。编导写"前进 1 米"而舞台位要求 2.3 米，
狗会静静停在错的位置上，现场没人看得出来。

所以 `validateShow()` 会在**开演前**拦住这类错：

| 检查 | 拦什么 |
|---|---|
| 动作 key 不存在 | 狗不认这条指令 |
| **高危动作**（空翻那一类） | 演出是连着播的，塞一个空翻 = 连着甩出去，场地不够就摔 |
| cue 超出总拍数 | 永远不会触发 |
| 位移量与舞台位对不上 | 走不到位（开环的必然要求） |
| 单段位移 > 5 米 | 开环走太远会累积误差 |

校验结果在网页端直接标红，保存时也随响应返回。

## 5. 灯光联动：只有链路，没有驱动

本仓库**没有任何灯光硬件驱动**（没有 DMX / Art-Net / 灯光台协议的实现）。
所以这里做的是**联动链路**：

- `LightSink` 是窄接口：`fireCue(灯号, 参与角色)`；
- 默认实现 `LoggingLightSink` 只记日志，并保留最近 64 条事件；
- 要接真灯光时，实现自己的 `LightSink` 塞进 `ShowEngine::setLightSink()` 即可
  （DMX / OSC / MQTT / 串口…）。

> ★ **接上 LightSink ≠ 灯会亮**。目前能保证的是"时间轴上的灯光 cue 在该亮的时刻被准时触发"，
> 下游怎么用由接入方决定。

## 6. 怎么用（网页编导台）

顶栏「⋯更多 → 多机编队」，或直接打开 `http://127.0.0.1:8123/?page=show`。

1. **新建演出** —— 填名称、BPM、总拍数。
2. **时间轴页**：点拍格放 cue。
   - 已有 cue 的那一拍 → 选中它；空白拍 → 新建一条动作 cue。
   - 每条 cue 可改类型（动作 / 位移 / 灯光）、所在拍、参与角色。
   - 角色不选 = 全体；勾选 = 只有这几台做。
3. **队形页**：舞台俯视图（1 格 = 1 米，箭头是朝向）。
   - 「＋ 加一个位」摆出队形 → 填 x / y / 朝向 → 下拉指派哪台狗站这个位。
   - 一台狗只能站一个位（在别处站着的会被自动挪过来）。
4. **保存** —— 落盘 `robot_shows.json`（运行目录）。
   校验问题会当场回显。
5. **开演** —— 需要先在「设备」里勾选受控设备（受控 ∩ 就绪 = 参与集合）。

演出中：顶栏显示同步度量；「停止演出」= 中止 + 给参与的车停车。

## 7. HTTP API

| 指令 | 说明 |
|---|---|
| `show_save` | 新增/更新一场演出（整份 `show` 上来），返回 `id` 与 `problems`（静态校验结果） |
| `show_del` | 删除一场演出 |
| `show_play` | 开演（可选带 `ips`；不给就用当前受控∩就绪集合） |
| `show_stop` | 停演（中止 + 停车） |

`GET /api/state` 新增：

- `shows[]` —— 全部演出，每项带 `count`（cue 数）与 `problems`（校验问题）
- `showState` —— 引擎实时状态：`running` / `name` / `cuesTotal` / `cuesFired` /
  `robots` / `maxSkewMs` / `avgSkewMs` / `lateCues` / `maxLatenessMs` / `error`

`robots[]` 每项新增 `deviceKey`（`sn:` / `ip:` 前缀）—— 编队指派与角色都用它。

## 8. 安全语义

**急停是唯一入口，演出绕不过它。**

演出引擎复用 `UiState` 的**代际号**（`scriptGen`）作为自己的身份：

- `cmd::estop` / `cmd::abortScript` 自增代际号 → 引擎立刻察觉并收尾；
- 引擎自己也是"当前脚本"之一 → 界面顶栏显示"演出：xxx"、网页端"正在播放"状态自动成立。

所以不存在"演出绕过急停"这种可能：两边共用同一个代际号。

另外三处安全约束：

1. **动作 cue 触发前先给正在位移的车补一条 StopMove** —— 四足不能一边走一边做动作（空翻更会摔）。
2. **位移 worker 中止时必须补发停车** —— 急停的 StopMove 与 worker 的补发之间可能差一个节拍
   （100ms），少这一条，"急停后狗还在滑行"就是必然的。
3. **高危动作不进演出**（静态校验拦 + 运行时二次拦），与舞蹈编排同一条纪律。

## 10. 已知限制

1. **没有里程计** → 队形换位是开环的，走久了会累积误差；**每场之前要做地面标定**。
   要闭环得换带里程计的机型（如 Go2 Pro 的网口 DDS 通道）—— 那是另一件事。
2. **没有灯光驱动** → 只有联动链路（§5）。
3. **同步误差受网络限制** → 实测量级 10~40ms；WiFi 差/多机共道干扰时会变差，
   这就是"迟到条数"与"最大错位"存在的意义。
4. **单机换位最远 5 米**（静态校验拦）—— 超过请拆成多段，中间加停顿重新标定。
5. **编队与「舞蹈编排」不互通** —— 两套独立的数据模型与播放路径（§0）。
6. **网页端"可视化"是俯视示意图**，不是实时定位图 —— 它画的是**编导意图**，不是狗的实时位置。

## 11. 与 SomaFlow 的差距（如果要继续对标）

SomaFlow 闭源，只能从它的公开描述推断其能力边界。以下是我们**目前没有**的：

- **闭环队形控制**：他们宣称"数十台高精度编队 + 毫秒级同步 + 分布式决策"，
  其中"分布式决策"意味着机器人之间要能互相协商位置 —— 这需要每台狗有定位能力，
  我们的 Go2 走不到那一步（除非换机型或走 DDS 通道拿里程计）。
- **规模**：我们没做过 10 台以上的并发验证；并行下发是每台一个线程，
  几十台时的线程数与网络压力需要实测。
- **编队自动生成**：SomaFlow 那边看起来有"阵列展开 → 穿插重组"的自动编排，
  我们现在是手工摆位。
- **与灯光台的真对接**（§5）。
