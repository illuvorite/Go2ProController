# 同时连接 Go2 Air + 两台 Go2 Pro：原因分析、改造方案与验证方法

> 适用版本：本仓库 `client/`（C++ WebRTC 控制管理台）+ `go2_network_diag/`（网络诊断工具）
> 协议依据：`docs/go2_webrtc_protocol.md`（实测）+ 官方同源参考实现 `legion1581/unitree_webrtc_connect`（源码交叉验证）

---

## 0. 结论摘要（先看这里）

**协议层面 Air / Pro / EDU 完全相同**（参考实现里三者共用同一套信令、同一套话题）。
"Air 能连、Pro 连不上"不是机型差异，而是下面 4 类原因之一，按出现概率排序：

| # | 原因 | 现象特征 | 处置 |
|---|---|---|---|
| 1 | **Pro 固件 ≥ 1.1.15 → `data2=3`，需要"每设备 AES-128 钥匙"** | `con_notify` 能取到，但客户端报 `data2 = 3 ... 需要每设备 AES-128 key`；日志卡在"信令交换中" | 用官方 App 绑定的宇树账号登录客户端顶栏「云账号」拉钥匙；或 `--keys <32位hex>` |
| 2 | **Pro 固件 < 1.1.11 → 只有 `:8081` 明文 `/offer`，没有 `:9991`** | 端口探测只有 8081 通；旧代码只探测 9991 → 直接判定"端口不通" | 客户端已支持双流程（9991 优先，回退 8081），无需钥匙 |
| 3 | **网络模式/位置不同**：Pro 还停在 AP 模式（自己发热点，192.168.12.1），或连了另一个路由器/频段/网段 | `ping` 不通；扫描扫不到；两台 Pro 的 IP 不在同一 /24 | 在官方 App 里把三台都改成 STA 连同一路由器；AP 模式只能单台直连（一台 WiFi 网卡同一时刻只能在一个网络里） |
| 4 | **会话被占用**：手机 App / 上一轮失败的会话没释放 | HTTP 200 但 `sdp == "reject"`，或 `con_notify` 无有效响应 | 断开手机 App，等 10~20 秒；客户端已自动退避重连（2/4/8/16/30s） |

次要但必查的两项：**多网卡（WSL/Hyper-V/VMware 虚拟网卡）导致 ICE 选错路径**；
**同时握手把机器狗单线程信令服务堵死**（三台一起点时最容易踩）。

本仓库已按上述结论完成改造，新增能力见 §6、§7，验证方法见 §8。

## 1. 现状：链路到底怎么走的

```
电脑 ──(WiFi/有线, 同一局域网)── 机器狗 WiFi 侧
                                  ├─ :9991  WebRTC 信令（Boost.Beast，单线程 accept）
                                  │        GET  /con_notify      → base64(JSON{data1,data2})
                                  │        POST /con_ing_<path>  → 加密交换 SDP
                                  └─ :8081  旧固件明文信令
                                           POST /offer           → 明文 JSON 交换 SDP

收到 SDP answer 后：ICE → DTLS → SCTP → DataChannel("data") → validation 校验 → heartbeat 心跳
校验/心跳通过后才算"就绪"，才能下发运动指令
```

三个硬约束（改代码时不要破坏，详见 `client/README.md`）：

1. offer 里必须有 `m=audio` + `m=video` 两条 m-line；
2. offer 里只能有一条 `a=fingerprint`（sha-256）；
3. 构造 PeerConnection 时不要配 STUN（`config.iceServers.clear()`）。

另有两条机器人侧约束：

4. **同一时刻只允许一条 WebRTC 连接**（无 token 时）——所以"每台一个连接"是正确的多机模型，
   但**不能两台客户端连同一台狗**；
5. **不发心跳（2 秒）会被断开**。

## 2. Air / Pro 差异对照（实测 + 源码交叉验证）

| 维度 | Go2 Air | Go2 Pro | 影响 |
|---|---|---|---|
| WebRTC 信令协议 | 完全相同 | 完全相同 | 无差异 |
| 运动指令 / 话题 | 完全相同 | 完全相同 | 无差异 |
| 网口 | **无** | 有（192.168.123.161，DDS） | Pro 有网口；但**新固件的 DDS 是加密的，见 §12**，不是免钥匙通道 |
| 出厂固件版本 | 通常较旧（`data2=2`） | **可能较新（`data2=3`）** | ★ 头号差异，需要云钥匙 |
| 出厂 WiFi 模式 | 常见 STA（连路由器） | **可能仍是 AP（自己热点）** | ★ 不在同一网段就永远连不上 |
| 固件分界线 | `data2=2`：1.0.19~1.0.25、1.1.1~1.1.14<br>`data2=3`：≥ 1.1.15<br>8081 明文流程：< 1.1.11 | 同左 | 与机型无关，**只与固件版本有关** |
| AP 模式自身地址 | 192.168.12.1 | 192.168.12.1 | 此时 offer 的 `id` 必须是**空串**（STA 才是 `"STA_localNetwork"`） |

> 结论：**先查三台的固件版本与当前 IP/网段，再谈代码兼容**。同型号不同固件也会表现不同。

## 3. 可能原因分层排查（从下往上，逐层有判据）

### L1 网络层

| 检查 | 命令 | 判据 |
|---|---|---|
| 电脑有几个网卡、在哪几个网段 | `ip -4 addr`（Windows：`ipconfig`） | 三台狗应在电脑某个网段的 /24 内 |
| 三台狗是否可达 | `ping <ip>` ×3 | 三台都要通 |
| 是否被 AP 隔离/跨网段 | `traceroute <ip>` | 出现多跳网关说明跨网段（可能被拦） |
| 是否走到了虚拟网卡 | 看 `ip route get <ip>` | 出口应是 WiFi/有线网卡，不是 `wsl`/`docker`/`vEthernet` |

**处置**：三台都改成 STA 模式连同一路由器（官方 App → 设置 → WiFi）。若必须一台走 AP，
则那台要用 AP 地址 `192.168.12.1`，并且**电脑必须切到它的热点**——单网卡无法同时控三台。

### L2 端口/服务层

```bash
# 新固件
curl -sv http://<ip>:9991/con_notify
# 旧固件
curl -sv -X POST http://<ip>:8081/offer
```

| 结果 | 含义 | 处置 |
|---|---|---|
| 9991 200 且 body 是 base64 | 新固件，正常 | 继续 L3 |
| 只有 8081 通 | 旧固件（< 1.1.11） | 走 legacy 流程（客户端已支持） |
| 9991 通但 `/con_notify` 超时/无有效响应 | 信令服务被占用 | 断开手机 App，等 10~20 s |
| 两个都不通 | 不在同网段 / 未开机 / 防火墙 / IP 写错 | 回 L1 |

> 注意：机器狗信令服务是**单线程 accept**。裸 TCP 探测后直接 `close()` 会让它等
> Keep-Alive（约 4 s）才释放，期间后续 HTTP 全被堵死。本项目所有探测都做了
> `shutdown(SHUT_WR)` 优雅收尾；扫描工具也应如此。

### L3 握手层（这里是 Air/Pro 分叉的地方）

`GET /con_notify` 解密后看 `data2`：

| data2 | 适用固件 | 解密方式 | 需要准备什么 |
|---|---|---|---|
| 1（或缺省） | 极旧 | `data1` 已是明文 | 无 |
| 2 | Go2 1.0.19~1.0.25、1.1.1~1.1.14 | 内置静态 GCM key | 无（代码内置） |
| **3** | **Go2 ≥ 1.1.15** | **每设备 AES-128 key**（GCM 认证标签校验） | ★ 云账号里的 `dev.key` |

每设备钥匙的取得方式（三选一）：

1. 官方 App 绑定的宇树账号 → 客户端顶栏「云账号」登录（`login/email` + `device/bind/list`）；
2. 直接给 32 位 hex：`go2_remote --keys <hex>` 或 `keys.txt`（本地钥匙库）；
3. 从机器狗内部读取 `/unitree/etc/key/aes_key.bin`（需 SSH/越狱，不推荐）。

**两台 Pro 若绑在不同账号，必须分别登录**：钥匙会**累加**（`addAesKeys`），不会互相覆盖。
命中哪把由 GCM 校验决定，命中后按 IP 写入 `go2_keys_cache.json`，下次启动直接复用。

### L4 SDP / ICE 层

| 症状 | 原因 | 处置 |
|---|---|---|
| 日志显示多条 `a=fingerprint` | 机器狗 DTLS 静默失败 | 已由 `stripExtraFingerprints()` 处理 |
| SCTP `InitChunk` 无限重传 | 同上 | 同上 |
| ICE 卡在 `checking` | 候选地址里有不可达的虚拟网卡地址 | `--bind-route` 或 `GO2_KEEP_CANDIDATES=<本机正确地址>` |
| 之前 Air 走 IPv6 成功、Pro 不行 | 两台各自的 IPv6/DNS 环境不同 | `--ipv4` 只保留 IPv4 候选 |

### L5 校验/心跳层

- 收到 `{"type":"validation","data":"<key>"}` 后必须回 `base64(md5("UnitreeGo2_"+key))`，
  机器狗回 `Validation Ok.` 才算就绪；
- 就绪后必须每 2 秒发心跳；
- 若校验一直不完成 → 多半是**钥匙不对**（data2=3 拿错了钥匙，或 DK 与 SN 不匹配）。

### L6 多机并发层

- 三台一起点"连接"时，机器狗侧单线程信令服务 + 电脑侧并发握手会互相干扰，
  表现是"随机某一台失败"；
- 处置：**错峰连接**（本项目默认 600 ms 间隔）＋失败退避重连。

## 4. 具体排查步骤（可照抄执行）

```bash
# ① 三台信令体检（项目自带，推荐第一步）—— 会直接告诉你缺不缺钥匙
python main.py webrtc -i 192.168.2.111,192.168.2.112,192.168.2.113
# 未知 IP 时先扫网段（含 AP 网段）+ SN 多播发现
python main.py webrtc --scan --subnet 192.168.2.0/24 --subnet 192.168.12.0/24

# ② 单台连通性/端口（等价手工命令）
ping -c 2 192.168.2.112
curl -sv http://192.168.2.112:9991/con_notify      # 新固件
curl -sv -X POST http://192.168.2.112:8081/offer   # 旧固件

# ③ 客户端无界面验证（三台同时，含链路指标）
./go2_remote --verify 192.168.2.111,192.168.2.112,192.168.2.113 --seconds 60

# ④ 加动作回执校验（真正验证"能控"）
./go2_remote --verify 192.168.2.111,192.168.2.112,192.168.2.113 --seconds 40 --actions

# ⑤ 多网卡环境仍失败时再试这两把
./go2_remote --verify ... --bind-route      # 按路由绑定正确网卡
./go2_remote --verify ... --ipv4            # 丢掉 IPv6 候选
```

判据（每一步的"通过"标准）：

| 步骤 | 通过标准 |
|---|---|
| ① | 三台都出现 `9991 开放` + `data2`；`data2=3` 的必须显示"钥匙已备" |
| ② | 新固件返回 200 + base64；旧固件 `/offer` 返回 200 |
| ③ | 报告里三台 `状态=就绪`、`最近(ms) < 5000`、`稳定(s) ≥ 测量时长×80%` |
| ④ | 每台都有 `[回执] ... code=0 (成功)`，无 `code != 0` |

## 7. 多机管理与切换策略

### 7.1 连接与保活

- **一机一连**：`RobotManager` 为每台狗维护一个独立 `RobotClient`（独立 PeerConnection / DataChannel / 心跳线程）。
  绝不共用连接，也不允许两台客户端连同一台狗。
- **错峰上线**：`connectAll(ips, 600ms)` 按 600 ms 间隔排队发起，避免同时握手堵死单线程信令服务；
  实测三台一起点的失败率明显高于错峰。
- **失败重试**：信令阶段 3 次（1.2/2.4/3.6 s）；通道建立+校验总超时 20 s；
  之后的掉线交由监督线程按 2→30 s 退避重连，直到用户手动断开（`desired=false`）。
- **掉线判定**：就绪后 12 s 收不到任何数据（心跳应答/状态话题都算）判定掉线 → 重连。
- **断开安全**：任何断开路径都先 `StopMove`（避免狗保持最后速度），再关 DataChannel/PC，
  保证机器人侧及时释放会话（否则下次会 `reject`）。

### 7.2 控制与切换

| 场景 | 策略 |
|---|---|
| 单控 | 设备列表勾选 1 台 |
| 群控 | 勾选多台；所有控制指令走 `forEachSelected` 逐台下发 |
| "单控 ↔ 群控"切换 | 只改勾选状态，**不断开连接**（连接与受控是正交的两件事） |
| 急停 | 红色「急停」按钮对**所有就绪**的狗发 `StopMove`（不限于勾选），最安全 |
| 摇杆/转向 | 按住时 10 Hz 群发，松手立即对所有受控狗发 `StopMove` |
| 单台故障 | 该台自动重连，**不影响**其它两台（连接、心跳、订阅完全独立） |
| 动作类指令 | 逐台顺序下发并留间隔（`--actions` 即按此实现），避免广播风暴 |
| 状态回传 | 每台就绪后订阅 `rt/sportmodestate` + `rt/lf/lowstate`，UI 日志带 `[IP]` 前缀区分 |

### 7.3 钥匙与设备身份管理

- 账号 → 设备列表（SN/别名/`key`）；握手成功后把"IP ↔ 钥匙"绑定并写入缓存；
- 缓存文件 `go2_keys_cache.json`：`{ "192.168.2.112": "<32hex>" }`，下次启动零成本命中；
- 未命中时回退为"候选池逐个试"（GCM 标签校验通过即命中），仍失败则明确报"钥匙不属于这台狗"。

## 8. 如何验证两台 Go2 Pro 均已成功连接并可稳定通信

### 8.1 三层验证

**第 1 层：信令可达性（不需要客户端）**

```bash
python main.py webrtc -i <air_ip>,<pro1_ip>,<pro2_ip>
```
通过标准：三台都 `9991 开放`；`data2=3` 的两台显示"钥匙已备"。

**第 2 层：连接与数据流稳定性（核心）**

```bash
./go2_remote --verify <air_ip>,<pro1_ip>,<pro2_ip> --seconds 60
```
程序会：错峰连接三台 → 各自订阅状态话题 → 每 2 秒心跳 → 结束时打印报告。
**通过标准（三台都要满足）**：

| 指标 | 阈值 | 含义 |
|---|---|---|
| `状态` | 就绪 | 校验 + 心跳通道建立成功 |
| `最近(ms)` | < 5000 | 5 秒内仍有机器人数据回传（不是"假在线"） |
| `稳定(s)` | ≥ 测量时长 × 80% | 60 s 测试里至少 48 s 在线，容忍偶发重连 |
| `重连` | 0 最好，≤1 可接受 | 反复重连说明 WiFi/信道不稳或钥匙/会话有问题 |
| `心跳ok/发` | 基本相等 | 应答缺失说明上行通、下行丢 |
| 退出码 | `0` | `0=全部达标`，`2=有设备未达标` |

**第 3 层：控制链路可用性（动作回执）**

```bash
./go2_remote --verify <air_ip>,<pro1_ip>,<pro2_ip> --seconds 40 --actions
```
每台依次执行 `BalanceStand(1002) → Hello(1016) → StopMove(1003)`，逐条校验回执
`data.header.status.code == 0`。**通过标准：每台 3 条回执全部 `code=0`。**
（动作前请把狗放在地面附近、周围无人，不要在桌面上做动作测试。）

### 8.2 稳定性压测（建议 10~30 分钟）

```bash
./go2_remote --verify <ip1>,<ip2>,<ip3> --seconds 1800 --actions 2>&1 | tee verify_1800s.log
grep -c "重试\|连接失败" verify_1800s.log     # 期望 0 或个位数
```
观察点：`稳定(s)` 是否接近总时长、`重连` 次数、`心跳ok/发` 是否收敛、
是否有某台反复失败（→ 那台单独排查 WiFi 信号/信道/共道干扰）。

### 8.3 不达标时的对照表

| 报告里的现象 | 最可能原因 | 下一步 |
|---|---|---|
| 某台一直是"失败"，错误含"9991 与 8081 都连不上" | 不在同网段/AP 模式 IP 用错 | 用 §4 的 ① 体检该 IP；AP 模式用 192.168.12.1 |
| 某台错误含"data2 = 3 ... 需要每设备 AES-128 key" | 缺钥匙 | 云账号登录或 `--keys` |
| 某台错误含"候选 AES key 均未通过 GCM 校验" | 钥匙不属于这台（SN 不匹配） | 用该台绑定的账号登录；两台 Pro 分别登录 |
| 错误含 `sdp reject` | 被手机 App/旧会话占用 | 断开 App，等 10~20 s（客户端会自动重试） |
| 就绪后很快掉线、`重连` 数很高 | WiFi 弱/共道干扰/路由器省电 | 靠近 AP、换 5 GHz 或固定信道、关 AP 隔离；必要时 `--bind-route` |
| 一台成功、另一台 ICE 卡住 | 多网卡候选干扰 | `--bind-route` 或 `GO2_KEEP_CANDIDATES=<本机正确地址>`；必要时 `--ipv4` |
| 三台一起点时随机失败 | 并发握手堵住单线程信令服务 | 用「全部连接」（已错峰 600 ms），不要三台同时手点 |


### 9.2 新发现的四个坑（都已修进代码）

1. **`con_notify` 返回 HTTP 429 —— 信令限流**
   短时间内反复连接同一台狗（秒级间隔）会触发。此时**即使握手成功，最初几秒下发的运动指令也会被拒（回执 `code=-1`）**。
   → 已做：识别 429 并给出明确提示；限流时重试退避 ≥8 秒；管理器自动重连退避改为 **5→10→20→30 秒**。
   → 纪律：**重连间隔建议 ≥15 秒**，不要脚本化地连续重连同一台狗。

2. **刚就绪就发指令会被拒（`code=-1`）**
   实测：会话建立后 1~2 秒内下发 `BalanceStand/Hello` 返回 `-1`，延时后同一条指令返回 `0`。
   → 已做：`--settle`（默认 2500ms，验证模式）+ 客户端"被拒后 900ms 自动重试一次"兜底。

3. **状态主题名随固件不同**
   192.168.2.107 **只发 `rt/lf/sportmodestate` / `rt/lf/lowstate`**，不发 `rt/sportmodestate`；
   订阅错主题会导致"显示无状态、电量/模式为空"。
   → 已做：两套主题都订阅。

4. **运动模式是 `mcf`，切 `normal` 被拒（`code=7004`）**
   该模式下运动指令照样执行，不需要强行切模式。若要查询/切换：
   `rt/api/motion_switcher/request` + `api_id=1001`（查）/ `1002` + `{"name":"normal"}`（切）。

### 9.3 一个必须记住的客户端 Bug（已修）

`pc_->onLocalDescription([&]{...})` 原实现捕获了 `runSignaling()` 的**栈局部变量**。
该回调由 libdatachannel 内部线程异步调用，且**可能在函数返回之后**再次触发（ICE 收集完成 / SDP 重新生成），
于是变成 use-after-free —— 现象是**随机段错误**（本次表现为：连上后约 1 秒、在 ICE 阶段崩溃，
`si_addr` 是野指针，重启客户端有时又能连上）。
→ 已改为捕获 `shared_ptr` 堆状态。**排查同类"随机崩溃"时优先怀疑这类跨线程回调的悬垂捕获。**

### 9.4 交叉验证方法（推荐留作排障手段）

本机已把参考实现（`/root/go2ref`）的依赖装进项目 `.venv`（`aioice / aiortc / pycryptodome / curl_cffi / wasmtime / requests`）。
它是**另一套完全独立的 WebRTC 协议栈（aiortc）**，用来区分"机器人问题"还是"我们客户端问题"非常有效：


实测结论：aiortc 能连上而 C++ 客户端崩溃 → 问题在客户端（最终定位为上面的悬垂引用）。

## 10. 风险与注意事项

- **单接口限制**：一台 WiFi 网卡同一时刻只能处于一个网络。三台狗必须同网段（都 STA 到同一路由器）；
  若某台坚持 AP 模式，需要额外的无线网卡（或用有线接 Pro 的 123 网段走 DDS，但 Air 无网口，无法统一）。
- **固件混用**：同一网络里同时存在 <1.1.11（8081）、1.1.x（data2=2）、≥1.1.15（data2=3）三种行为是允许的，
  本项目已全部兼容；但排查问题时建议统一升级，减少变量。
- **唯一的连接配额**：任何时刻不要用手机 App 或第二个脚本连同一台狗，否则必然 `reject`。
- **安全**：`go2_keys_cache.json` 与 `keys.txt` 含每设备 AES-128 钥匙，属于敏感文件，不要提交到版本库
  （已在 `.gitignore` 语义之外，请自行加入忽略规则）。
- **动作安全**：`--actions` / 群控动作前确保周围无人；运输/搬运前先「阻尼」或关机。

## 12. 有线 DDS 通道实测结论（2026-09-23）：新固件下**不是**免钥匙通道

早期方案里有一条诱人的假设：**"插网线 → 内网 192.168.123.0/24 → DDS 控制，不需要钥匙"**。
在 **Go2 Pro（固件 ≥ 1.1.15，`data2=3`）** 上实测**不成立**。现场条件：网线直连狗网口，本机 `192.168.123.100/24`，
狗 WiFi 侧 `192.168.0.169`（同一台设备，MAC `78:22:88:b5:22:fe`）。

| 观测项 | 实测结果 |
|---|---|
| 内网二层/ICMP | 通（`ping 192.168.123.161` 0.4~5 ms） |
| 内网服务 | **只有 9991**（信令，同样要求 `data2=3` 钥匙）；无 22 / 5555 / 2049 / 8080 |
| 狗的 DDS 多播 | `239.255.0.1:7400`（发现：明文 SPDP/SEDP）+ `239.255.0.1:7401`（用户数据，**≈1 MB/s**） |
| `7401` 载荷 | **全部是 DDS Security 子消息**：`0x30`(SEC_PREFIX) / `0x31`(SEC_POSTFIX) / `0x32`(SEC_BODY)，高熵、零明文（AES-GCM 加密） |
| 明文 SPDP 主动探测 | 手工发 32 个 SPDP（`0x15`、`0x02` 两种 DATA 编码）→ 收到狗侧多播 131 + 1801 包，**单播回应 0 个** |
| 官方 SDK（`unitree_sdk2py`，WSL 与 Windows 原生各两种配置） | 收不到任何 topic 帧（0 帧） |
| SPDP 里明文可见的节点名 | `robot_state_service`、`unitree_lidar_server`、`voxel_height_mapping_dds_node`、`unitreeWebRTCClientMaster` |

**结论：**

1. 该固件对 DDS **用户数据启用了 DDS Security（加密 + 签名）**，并且**不匹配未认证的明文参与者**
   → 标准 CycloneDDS / 官方 SDK 客户端既读不到数据，也写不进指令；
2. 所以"有线 DDS = 零钥匙控制"这条捷径**只对旧固件（≤ 1.1.14，`data2=2`）有效**，
   对 `data2=3` 的新固件**不可用**，不要再在这条路上耗时间；
3. 该设备的钥匙只有三个来源：**① 绑定过这台狗的宇树账号（推荐、唯一干净路径）；
   ② 设备内 shell（需 root 或硬件 UART 口，才能读 `/unitree/etc/key/` 或关掉 DDS 安全）；
   ③ 降级固件到 ≤1.1.14（但降级本身要先 root，形成循环）**。
